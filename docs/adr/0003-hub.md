# ADR-0003: Hub — topology, faces and auth, control and media planes

## Status

Accepted

Doc index: [../README.md](../README.md).

## Context

Open Automotive Assistant started as an on-car Android app: one Ktor process per head unit, LAN browsers talking to that HU. Open Home Foundation–friendly projects such as Music Assistant ship an **always-on server** beside Home Assistant, with endpoints (players / cars) joining that server, a shared web UI, Docker + HAOS app packaging, and a thin HA integration that discovers the server.

We need multi-car control from a home hub without moving VHAL / AAOS APIs off the car and without embedding the car stack inside Home Assistant. Cars must reach the hub while away (cellular), humans need a browser UI on and off the LAN, and vehicle control must never be anonymous on the internet. Camera media does not fit JSON RPC, and routing video through the hub would make it a media server that sees every frame from inside the car. Contributors also need to update and debug cars without adb in the normal loop.

## Decision

### 1. Topology

1. **Two host roles**, same protocol and SPA:
   - `local` — head-unit runtime (the APK). The car controls itself on `:8787`.
   - `hub` — always-on JVM process. Aggregates paired **nodes** (cars) and serves the same UI in fleet mode.
2. **Hub-and-spoke.** Hub-to-hub federation is deferred.
3. **Cars dial out** after pairing (hub URL + short-lived single-use pairing code → long-lived node token). The hub needs no inbound NAT to each car. Optional mDNS (`_oaa-hub._tcp`) advertises hubs on the LAN. On the LAN the hub can start pairing instead, confirmed by a code on the car ([ADR-0004](0004-car-auth.md)).
4. **Vehicle integrations stay on the node.** The hub never talks VHAL; it proxies the OAA HTTP contract to the car selected by the `X-Oaa-Node` header, then `?node=`, then the `oaa_node` cookie.
5. **Packaging:** one Docker image (`deploy/docker/Dockerfile`) for compose and the HAOS app. State lives under `/data`. Supported server installs are compose or the HAOS app.
6. **Home Assistant:** keep the inbound `:plugin-homeassistant` on the HU for car→HA shortcuts. Outbound automation uses a HACS custom component against the **hub**. OAA is not embedded in HA core.

### 2. Two network faces

| Face | Default port | Paths | Auth |
|------|--------------|-------|------|
| **Human** | `OAA_PORT` 8787 | SPA, control/events APIs, `/debug/*` proxy, signaling, OTA admin | Hub session (local password, HA OAuth, or Ingress headers) |
| **Node** | `OAA_NODE_PORT` 8788 | `/api/health`, `/api/nodes/pair`, `/api/nodes/session`, `/api/nodes/artifacts/{sha256}` | Pairing code → opaque **node bearer token** |

Login, setup and static assets may be public on the human face; entity and control APIs never are.

| Path | Auth | Use |
|------|------|-----|
| LAN human UI | Hub session | Home |
| LAN/VPN cars | Node token → node port | Home |
| **HA Cloud → node face** | Node token; HA views `requires_auth=False`, allowlisted to pair/session/artifacts | Away cars |
| Compose tunnel → node | Node token + TLS | Away cars without HAOS |
| Compose tunnel → human | Hub login (+ optional HA OAuth) behind TLS | Humans without HAOS |
| WebRTC media | Hub session on `/api/webrtc/signal`; DTLS car ↔ viewer | Remote Cameras |

### 3. Hub human auth

1. **Built-in** — bcrypt username/password; first-run setup creates the admin (no recovery → wipe `auth.json`).
2. **Home Assistant OAuth (IndieAuth)** — `/api/auth/authorize` when `OAA_HA_URL` + `OAA_HA_CLIENT_ID` are set. The callback exchanges the code at `/auth/token` and reads the identity from WS `auth/current_user`. HA users are matched by HA user id only, never linked to local accounts by username. HA admins become hub admins.
3. **Ingress** — in the HAOS app only, `X-Remote-User-*` headers are trusted when the peer is the Supervisor ingress proxy (`172.30.32.2`, override `OAA_INGRESS_PROXIES`).

Sessions are opaque tokens (`oaa_session` cookie or `Authorization: Bearer`). Roles: `admin`, `user`, `system`. `/debug/*`, pairing, node removal and OTA require `admin`.

### 4. Control plane

HTTP, `/api/events` and node frames over the node WebSocket. JSON frames are `{type, payload}`; versioned payloads carry `v: 1` and are checked in one helper (`OaaFrames.isCurrentVersion`).

| Frame | Direction | Purpose |
|-------|-----------|---------|
| `hello` | car → hub | name, integration, `app {package, versionName, versionCode, apkSha256}` |
| `rpc` / `rpc_result` | hub ↔ car | `{id, method, path, query, contentType, body \| bodyB64}` → `{id, status, contentType, contentDisposition, body \| bodyB64}` |
| `event` | car → hub | one `/api/events` message (`t`-shaped); the hub fans it out per car |
| `ota_offer` / `ota_status` | hub ↔ car | app updates (below) |
| `ota_available` / `ota_request` | hub ↔ car | the hub's release for this car and its policy; the car asks to install it (below) |
| `public_node` | hub → car | `{publicNodeUrl?, sessionPath}` on connect and on change; the car swaps its published dial-in URL (never drops it) |
| `log_subscribe` / `log_unsubscribe` / `log` | hub ↔ car | live app logs for `/debug/logs/stream` |
| `ping` / `pong` | both | keepalive |

RPC bodies are binary-safe (textual types as `body`, others base64) and capped at 2.5 MiB so a frame stays under the HA Cloud bridge's 4 MiB message limit; larger responses return 413. The same proxy serves `/debug/*` (admin only), so the Lab page, the debug export zip and live logs work through the hub.

### 5. Media plane

WebRTC between car and viewer; the hub relays signaling only and never carries, logs or stores media bytes. The control plane is not moved onto WebRTC, so Home Assistant, curl and third-party clients keep working without a WebRTC stack.

- **Signaling** only on the human face: `WSS /api/webrtc/signal?node=<id>`. The hub relays `webrtc_offer` / `webrtc_answer` / `webrtc_ice` / `webrtc_hangup` bound by `sessionId` and never parses SDP. A version mismatch is answered with `webrtc_hangup reason=version`. The viewer offers (recvonly H.264 + the `oaa-media` data channel); the car answers.
- **ICE:** `GET /api/webrtc/ice` returns STUN plus optional short-lived TURN credentials (coturn REST HMAC: `OAA_TURN_URLS` / `OAA_TURN_SECRET` / `OAA_TURN_TTL`). Long-lived TURN secrets never reach browsers or cars.
- **Live:** the car tees AccessUnits from the hardware mosaic encoder straight into an H.264 sample track (no second encode). The car-side stack is Pion via gomobile (`libs/oaartc`), because GeckoView embeds its own `org.webrtc` classes and native library.
- **Data channel `oaa-media`:** `dc_hello {v, sessionId, features, playbackContainer: "fmp4", chunkMaxBytes, maxTransfers}`; playback (`playback_open` / `playback_seek` / `playback_close`, fMP4 for MSE), downloads (`download_open {name}`, basename only) and cuts (`cut_request {fromMs, toMs}`). Binary frames are `u8 type | u32 reqId | u32 seq | u8 flags | payload` with flags `eof` and `init`.
- **Limits:** one session per car (a newer offer replaces the prior one, `reason=replaced`); at most 2 transfers per session; chunks ≤ 256 KiB; ≤ 128 relayed ICE candidates per session; signaling frames ≤ 64 KiB.
- LAN `role=local` keeps HLS and direct `/api/dvr/*` HTTP.

### 6. App updates (OTA) from the hub

- An admin uploads an APK to `POST /api/ota/artifacts` (max 256 MiB, last 5 kept, addressed by sha256) and starts `POST /api/ota/rollouts {artifact, nodes | all}`.
- Online targets get `ota_offer`; offline targets get it again on reconnect while their `hello` APK hash differs. A newer rollout supersedes older ones.
- The car downloads `GET /api/nodes/artifacts/{sha256}` with its node token (`Range` resume), verifies the hash, that the archive is its own package signed with its current certificate, and self-installs (silent on API 31+, system confirm dialog otherwise → `pending_user`).
- When the car's `hello` hash is a stored artifact, the offer adds `delta {from, sha256, size, path}`: an OADP patch (`libs/apk-delta`) that copies unchanged zip entries from the installed APK. The car rebuilds and hash-checks the APK before the same verification, falling back to the full download on any failure.
- Progress comes back as `ota_status`; `installed` is only trusted from the next `hello` hash.
- Release updates: the hub fetches the car APK published with its own version (GitHub Releases, `car-apk.json` manifest, hash-checked) and, after each `hello`, sends `ota_available {v, mode, sha256?, size?, versionName?, versionCode?, downloadSize?}` to cars on a lower version code of the same package. In `ask` mode the head unit sends `ota_request {v, sha256}` and the hub creates a one-car rollout. In `auto` mode the hub creates it without asking. To keep car downloads to a delta, the hub also fetches the release the car runs when its hash matches the car's `hello`.

### Forbidden

- Anonymous reads or writes of entities/controls
- Serving the human SPA or APIs on the node face
- Binding naked WAN ports without TLS (tunnel or HA Cloud)
- Pushing media through the hub

## Consequences

- `/api/status` always includes `role` (`local` | `hub`) and `version`; hubs add `fleet`.
- The SPA reads `role` and shows a fleet picker on hubs; local UX stays single-car.
- Dual listeners complicate firewall docs but give a clear ACL surface. Compose users set `OAA_PUBLIC_NODE_URL` when using tunnels.
- The Android app ships the Pion WebRTC library (`libgojni.so`, ~10 MB per ABI, ~4 MB compressed in the APK). Viewers behind symmetric NAT need TURN (compose profile `turn`).
- The first install on a car still needs adb; after that `oaa-setup hub-deploy` replaces `adb install` in the normal loop.
- Access control is coarse (any hub user may control any paired car; admins may debug and update them). Per-car ACLs, hub SFU/recording and hub-to-hub federation are future work.
- OpenAPI ([../openapi/open-automotive-assistant-v1.yaml](../openapi/open-automotive-assistant-v1.yaml)) is the wire contract for hub, HU, HA integration and future MQTT clients.
